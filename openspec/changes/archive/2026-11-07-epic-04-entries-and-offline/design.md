# Design — Epic 4: Entries & offline capture

## Context

Epic 3 shipped the permission furniture: `can_log_for` rows (role-sourced + explicit),
roles, per-member `visibility`, managed/dependent profiles (`profile_managers`), and
server write helpers in `src/features/*/{groups,permissions}/server/`. The app is
server-component-first with zero client-callable data routes — the only API route is
Better Auth's. There is no offline layer yet: no Serwist service worker is wired, though
`serwist` is the declared stack choice, and `manifest.ts` exists.

Epic 4 adds the first client-synced write surface, so the trust boundary moves for the
first time: writes will now also arrive from a client queue over HTTP. See proposal.md
for scope; this file is only the how.

## Goals / Non-Goals

**Goals:**

- One server-side entry assembler per read shape, so G10 has a single place to hold.
- A client-generated entry `id`, making sync an idempotent upsert with no conflict logic.
- An offline queue that is simple to reason about: one IndexedDB store, replay in order,
  server re-verifies everything.

**Non-Goals:**

- Any trend, direction or aggregate display (Epic 5 computes on top of `entries`; entry
  screens show values, verbs and timestamps only — no deltas, no verdicts).
- The group board (Epic 6), reminders (Epic 7), export (Epic 8).
- Real-time sync, multi-device merge UI, or conflict resolution UI. The append-only
  model makes them unnecessary.

## Decisions

### 1. Permission model before the data model

Write and read differ, so here is the contract first:

| Action | Check | Where |
|---|---|---|
| Create entry | `canLogFor` row (`role` or `explicit`) **or** subject is the logger | `src/features/entries/server/entry-writes.ts`, using the existing `canLogFor` helper |
| Edit / delete entry | Creator's user is the acting user, **or** acting user manages the subject profile | `assertEntryEditor` in `entry-writes.ts` |
| Read entries of subject S | Never via `can_log_for`. Uses `groupMemberships.visibility` of the acting profile for S (+ "own profile always readable") | `listEntriesForViewer` below |
| Read a note | Author's user and subject-or-author match only; withheld inside the assembler for everyone else | `listEntriesForViewer` strips `note` unless author |

**The named assembler for every filtered read:** `listEntriesForViewer({ viewerProfileId,
subjectProfileId })` in `src/features/entries/server/entry-access.ts` (mirroring the
existing `profile-access.ts` / `group-access.ts` shape). It joins visibility from
`group_memberships`, applies `deleted_at IS NULL`, strips notes to their author, and is
the only function any page or route may call to display entries. The sync endpoint
doesn't read entries at all — it accepts upserts and returns the per-entry verdict.

Weight-level visibility shows weight + timestamps + recorder; `weight_trend` shows
date/recorder with the weight withheld (no trend math exists yet — Epic 5 — so this
level still must not leak the value); `hidden` shows nothing about the subject. This is
rendered server-side; the client never decides.

### 2. Data model

`entries` table exactly as the epic prescribes, with these concrete choices:

- `id`: UUID, generated by the client (`crypto.randomUUID()`), no server default — the
  server rejects a create without one (the id is what makes the upsert idempotent).
- `recorded_by_user_id text NOT NULL` with **no foreign key**: attribution survives
  account deletion by design. Display falls back to the stored name captured at insert
  time (`recorded_by_name`, denormalized on insert) when the user no longer exists.
  The same denormalized pattern covers the editor (`edited_by_user_id` /
  `edited_by_name`).
- `measured_at`, `recorded_at`, `edited_at`: `timestamptz` (UTC storage). The group's
  timezone for measured-date rendering and day-Equality checks: the **existing
  `groups.timezone` column** (Epic 1 set it at creation with an IANA name, `UTC`
  fallback). No second timezone column is added to `group_settings`: one source of
  truth per group. Rendering resolves through `Intl.DateTimeFormat` with the group's
  IANA name.
- Note authorship: the note belongs to the entry's recorded-by **user**. Only that user
  ever sees or edits the note text (spec: "never be visible to anyone other than its
  author"); another editor (e.g. the subject) preserves it server-side without being
  able to read it.
- Soft delete via `deleted_at`; the assembler filters it — deleted rows stay for
  authorship evidence and error checks, invisible to every read.
- Weight validation: accepted range **1.00–300.00 kg** enforced at the trust boundary
  (server) and mirrored client-side from one shared Zod schema (`entries/validation.ts`);
  message: "El peso debe estar entre 1 y 300 kg."
- Indexes: `(profile_id, measured_at)` for history and `(group_id, measured_at)` for
  board/day-sheet reads.
- Migration is additive (`drizzle-kit generate` → `migrate`), one new table only (no
  settings column — see above); no data backfill; rollback = drop the table.

### 3. Sync transport: one batched POST, no GET route

`POST /api/entries` receives `{ entries: [{ id, profileId, groupId, weightKg,
measuredAt, recordedAt, note?, editedAt? }] }` (delete ops: `{ id, entryId, deletedAt }`)
and answers per-item `{ status: "saved" | "failed", reason? }` in Spanish. Serialization:

- The client never sends `recorded_at` for creates that actually happened online
  without… (kept simple: `recorded_at` is client clock — already the "time it was
  typed" semantics; `measured_at` is editable).
- Every item re-runs the write checks server-side at apply time. A permission revoked
  offline surfaces as `failed` with reason, kept in the queue for correction.
- Batch cap 50 entries; the queue flushes in pages.
- No GET on this route. Reads stay in server components. **Alternative considered and
  rejected**: REST GET + client cache — puts a second read path   outside the assembler and violates G10.

### 4. Offline queue: one IndexedDB store, ordered replay

`weight-tracker-ops` IndexedDB store: `{ opId uuid, type: "create" | "edit" | "delete",
entryId, payload, status: "pending" | "synced" | "failed", attempts, errorMessage,
createdAt }`. Replay in `createdAt` order; ops are naturally idempotent: create = upsert
on entry id, edit = absolute field values, delete = set `deleted_at`. Retries therefore
need no server-side op dedupe table — **alternative considered and rejected**: a
server-side `sync_ops` table for replay dedupe (one more table guarding against a case
absolute-value semantics already solve).

Flush triggers: `online` event, app mount, Background Sync (tag `entry-flush`),
iOS Safari, which lacks it, still flushes on the other two). The SW nudges the
client via `postMessage`; the page owns the queue and performs the fetch — the
queue stays in one place, in the window, so the UI can render its states directly.
The worker is a hand-written `public/sw.js` rather than a Serwist build:
`@serwist/next` only integrates with webpack and this project compiles with
Turbopack (Next 16). It implements the same surface — precached offline shell
(`/offline`, hydration-ready chunk graph included), cache-first static assets,
failed-navigation fallback, `sync` handler for `entry-flush`, and `postMessage`
nudges — with a `shortcut:` comment marking the change to Serwist when the
toolchain supports it. Requests stalled by a network-state switch are covered by
a 15 s fetch watchdog and a bounded (3×, 3 s) auto-retry inside the page hook.

Offline snapshot reads: history + sheet pages hydrate from a
`weight-tracker-snapshot` IndexedDB store (per subject, last payload the assembler sent,
with a fetched-at marker rendered as "sin conexión — datos guardados en tu dispositivo").
Updated on every successful server render hand-off. **Alternative considered**:
Service-worker Cache API for reads — poor fit for structured rows and it cannot be
pre-filtered by identity.

### 5. UI surfaces (Spanish copy, existing peach system)

- Weigh-in sheet at `home` (currently a placeholder): profile selector seeded with the
  group roster (log-permission-filtered), numeric key pad (`inputMode="decimal"`),
  measured-date field defaulting to today (editable, no window cap beyond "not in the
  future"), preview of the next person after save, queued/saved badges per entry.
- History on `profiles/[profileId]`: own history always visible to the member; other's
  history renders through `listEntriesForViewer` only. Measured vs recorded displayed as
  two lines, Spanish labels ("Medido el… · Registrado el…").
- Edit/delete affordances only when `assertEntryEditor` would pass for the acting user,
  and always additionally enforced server-side.

### 6. Verification of the guardrails this epic touches

- **G10**: integration tests hitting the render path through `listEntriesForViewer` for
  every visibility level × note-author matrix; plus a test asserting no route returns
  membership+entries unfiltered. Shipped before anything else in this epic merges.
- **Write ≠ read (§2.3)**: integration test — after creating an entry for a `hidden`
  subject, the recorder still receives an empty history read.
- **G2/G3/G5**: copy review of the new surfaces: no delta numbers, no verdict language,
  no nudges (entry screens show values and verbs only).
- **G6**: the sheet derives nothing from the goal; goal fields are never read by
  `entry-writes` (asserted by an integration test that a subject with no goal can still
  be recorded).
- **G9**: dependents are recordable via managed-profile access, and their entries show
  only weight/timestamps (no target/progress UI exists — tests lock that no goal join
  happens in `listEntriesForViewer`).

## Risks / Trade-offs

- [Clock skew makes `measured_at` wrong] → measured date is explicitly editable; the
  recorded instant stays the server-adjacent client clock both sides accept.
- [Duplicate entries from retried sync] → client UUID + upsert on id; test flushes the
  same queue three times and asserts one row.
- [Safari lacks Background Sync] → `online` event + app mount are the reliable path;
  BG Sync is an enhancement, verified only on Chromium in tests.
- [Offline snapshot leaks data of a subject whose visibility dropped] → snapshot is
  cleared for a subject on next online render; offline staleness is honest
  ("datos guardados en tu dispositivo"); server reads always re-filter.
- [Queue grows unbounded offline] → 50-per-batch flush, attempts counter, failed ops
  stay for correction; queue UI shows pending count.

## Migration Plan

1. `drizzle-kit generate` (entries table + `group_settings.timezone`), review SQL,
   `drizzle-kit migrate` against local Postgres on port 5435.
2. Ship server feature + assembler + sync endpoint with G10 integration tests first;
   UI next; Serwist shell last. Each step lands buildable.
3. Rollback: revert migration (drop table + column). Nothing pre-existing is mutated.

## Open Questions

_None blocked. The `group_settings.timezone` default (UTC when unset) is a data choice
the owner can change from group settings; it does not affect this epic's behavior
beyond rendering._
